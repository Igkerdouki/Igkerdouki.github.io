05 — SpecCheck Early

Don't read the code. Run it.

AI code reviewers read a diff and guess whether the pull request does what the ticket asked. SpecCheck turns each requirement into real calls against the running app — moving the clock forward when the ticket talks about time — and posts a verdict with the evidence attached.

The question

Did the AI actually build what the ticket asked for?

More and more pull requests are written by a model, and more and more of them are reviewed by one too. Both sides of that exchange are reading text. The reviewer sees a diff that looks like a lockout feature and says it looks like a lockout feature.

What nobody has done is start the app and try to log in four times. The tools that read the ticket never run the code, and the tools that run the app are not looking at the ticket. SpecCheck sits in that gap: ticket in, executed checks, one verdict per requirement.

A reviewer that reads the diff is guessing. One that runs it has evidence.

How it works

A ticket becomes a list of things to try

Write the ticket as a spec

Each requirement becomes a short list of executable steps: HTTP calls, the status each one should return, and advance_minutes to move a fake clock.

Run every requirement from a clean state

SpecCheck starts the app with test hooks on, resets it before each requirement, and records every request and response as it goes.

Post the verdict on the pull request

The result is a Markdown report with the full trace behind each verdict. A GitHub Action comments it on the PR and fails the check if any requirement is not met.

✅ Met

The check ran and passed. The trace is attached.

❌ Not met

The check ran and failed. The trace shows exactly which call went wrong.

⚠️ Couldn't verify

The environment broke, or the requirement is too vague to test.

The demo

An off-by-one that reads perfectly fine

The ticket: "After 3 failed login attempts, lock the account for 15 minutes. Login should be secure." The demo app is a plausible AI-written implementation of it, with one bug — it locks on the fourth failure instead of the third. In a diff, that is one comparison operator. Run against the app, it is this:

R1 — after 3 failed attempts, a correct password is rejected POST /login wrong password → 401 expected 401 ✓ POST /login wrong password → 401 expected 401 ✓ POST /login wrong password → 401 expected 401 ✓ POST /login correct password → 200 expected 423 ✗
R1 · ❌ Not met
After 3 failed attempts, a correct password is rejected.
R2 · ❌ Not met
The account is still locked 14 minutes later.
R3 · ✅ Met
The lock expires after 15 minutes — checked by moving the clock 16 minutes forward.
R4 · ⚠️ Couldn't verify
"Login should be secure." Too vague to test; the report asks for a checkable criterion instead.

With the bug fixed, R1 and R2 turn green and R4 stays exactly where it was.

The third verdict is the one I care about. A tool that has to answer yes or no will eventually say yes to "login should be secure." SpecCheck is allowed to say it does not know — and that refusal is more useful to a reviewer than a confident pass that checked nothing.

Design decisions

Keeping the checker honest

Spec from the ticket
A language model drafts the spec from the ticket text and a description of the API. It never sees the pull request's code, so the checks reflect what was asked for, not what was built.
A human approves once
Drafts are saved separately and reviewed before they count. Steps that call endpoints missing from the API description are flagged before approval.
Time is a first-class step
"For 15 minutes" is the kind of requirement that never gets tested by hand. A fake clock makes it one line in the spec.
No dependencies
The runner is plain Python standard library, so adding it to a repository is copying a folder and a workflow file.

Where it goes next

Database assertions — a before-and-after diff of Postgres state, for requirements an HTTP status cannot show. Reading tickets straight from GitHub Issues and Linear. And support for a real framework, FastAPI or Express, in place of the standard-library demo app.
